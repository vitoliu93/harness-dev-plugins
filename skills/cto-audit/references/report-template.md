# 审计报告骨架（九段，`no-ai-slop` 汇报模式口径）

证据规则贯穿全文：**每个论断配数字或 file:line**；issue 根因 ↔ 代码证据 ↔ 历史模式三方互证；子代理结论未经主上下文抽验不进报告。读者是 CEO：方向/结果/需要拍板什么，行级细节不进正文（已移交 code-simplify 的只留一行交接说明）。

## 1. 总体判断（一句话开头，不铺垫）

质量经济学句式：「交付速度 X，但质量经济学倒挂：缺陷占工作项 N%、fix 提交 M%——约几成产能在返工。根因是结构性的：<一句话根因>。」

## 2. 关键数字仪表盘

一张表：缺陷率 / fix 比例 / 代码量分布（受管控 vs 游离）/ 配置契约面 / CI 测试环节数 / issue 关联率 / 改动放大系数（一个典型需求动几个模块）等。每行带「含义」列。

## 3. 结构性缺陷（3~5 个，按严重度排序）

每个缺陷固定三段：**问题**（现象+量化）→ **证据**（file:line / 命令输出 / issue 编号）→ **动作**（具体到可排期）。
带 P0/P1/P2 标注。安全类合并成至多一条、点到为止（见 SKILL.md 权重铁律）。

## 4. 领域偏离与模块缺陷聚类

- 盲画蓝图 vs 真实结构的 diff 三类偏差：隐藏领域概念 / 实现债模块 / 被稀释的领域边界
- issue 路取证：哪个模块缺陷密度最高、什么类型反复出现、复发说明缺什么机制

## 5. 规则变更公示（必有——CEO 的否决抓手）

三小节，各一行一条，每条一句话理由：

- **立**：新规则 + 适用条件（触发场景）+ 落成了什么工件（宪法断言/CLAUDE.md/ADR/词表）
- **改**：调整了哪条 + 为什么原版不再成立
- **废**：化石规则 + 适用条件为何已不存在

无变更也要写「本次无规则变更」。

## 6. 流程与习惯

小表格：issue 关联率、巨型提交、self-merge、身份碎片、tag 体系、测试目录卫生。每行给低成本修法。

## 7. 值得肯定（必有，绿色调）

点名好实践 + 建议「保持并推广」。审计不公允则失去公信力，这一节不可省。

## 8. 战略层思考（1~2 条，CEO 拍板清单）

只放机器和 CTO 都无法自决的取舍：债现在还还是养着、边界该不该重切、方向二选一。有理由、有代价评估。压缩到最少——分流阶段能落 harness 或移交 code-simplify 的不许出现在这里。

## 算法层二阶段报告（追加时）

- 按域分组（召回/对齐/LLM/管线/数据），每域 2~4 条
- 每条锚定 issue 证据或量化成本，不给教科书泛论
- 收尾一个「核心观察」：通常是「不缺想法、缺闭环」类的结构性总结 + 优先级表

## 交付变体

- HTML：仪表盘开屏大数字 + 缺陷编号卡（P 色带）+ 模块条形图 + roadmap 泳道 + 绿色「值得肯定」收尾；全中文为主避免术语堆砌；自包含无外链；深浅色 + 移动端可读
- 飞书：云盘上传 + 组织内链接可读 + 群发链接（不走文件消息）
- advanced-plan：goal（Done means 对齐路线图）/ spec（approach + key decisions + risks）/ todo（P0~P2 可认领 phase，各带 Acceptance）/ exploration（全部取证事实编号存档）
