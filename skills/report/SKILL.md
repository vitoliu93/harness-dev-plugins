# report — 给 CEO 的收尾汇报

**受众模型,一切规则由此推出:** 用户是 CEO——管方向、节奏、资源,不碰代码。
他看完汇报能做的动作只有三种:① go;② 纠方向 / 补业务上下文;③ 给资源(权限、key、预算、外部信息)。
任何不服务这三个动作的信息都是噪音。历史证据:过去充斥代码细节的汇报,用户回复几乎全是
"go"——那些细节从未参与决策。

## 四问框架

汇报正文只回答这四问,按序:

1. **成了没** — 第一句就是结论:done / partial / blocked,加一句话人话说明。
2. **质量如何** — 说*行为*,不说*实现*:"下载接口现在能拿到点赞转发数,真实视频上跑通了",
   而不是"在 `media_api.py` 的 `fetch_detail` 里加了 `statistics` 字段"。验证过就说怎么验的;
   没验证就明说没验,不粉饰。
3. **有什么要注意** — 风险、取舍、和原目标的偏离,用业务语言。没有就跳过这一节。
4. **需要你做什么** — 没有就写"不需要你做任何事"。有就一条条列,每条必须是
   方向级或资源级的动作,不是实施选择。

**长度:一屏内。** 超一屏说明还没做完"选重点"的工作——细节留在自己脑子里,不是转嫁给读者过滤。

## 问题设计铁律

发问前自测:**如果用户只可能回 "go",这个问题就不该问。**

- 可逆的实施决策 → 自己拿主意,做完在汇报里报结果。
- 真需要拍板的 → 把问题升到方向级:给 2 个真实选项 + 各自的业务后果,让"选哪个"
  不需要读代码就能答。
- 缺上下文卡住的 → 直接问缺的那个业务事实,别附一页技术铺垫。

## 细节去哪

留在会话里。汇报结尾一句"细节都在,想看哪部分说一声"即可。
用户追问时再按需展开——那时给全量技术细节是正确的,本 skill 不拦。

## 示例(取自真实会话;抽查 10 个收尾汇报,5 个是坏例,用户回复几乎全是"go")

**坏例一(征询类,标识已虚构化)** — 原文:"你批准的护栏加在 `absorbDuplicateEntry`,但那里只能
`return null`(→标 failed→重试循环)…真正的'关闭去重'要在更上游的 `resolveContentReuse`…
护栏维度要 `(tenant_id, store_type)` 两个…回 `go` 开工。" 用户回复:"go"。
改写:"查清了:高光召回为 0 的根因是不同品牌的同内容文件被错误地合并去重。修法是按品牌隔离,
外加订正已污染的数据、端到端复测。改动可逆,我直接开工,做完汇报。"——升级后连问都不用问。

**坏例二(收尾类)** — 原文:"…补齐 search 侧全部防线(跨品牌 scope 防线/PDF 页排除/黑屏过滤/
元数据过滤字段生效);会话素材目录加文件锁+原子写;CLI 失败统一 stdout JSON…单元 92+ 全绿…
回个 OK 我就走 finalize。" 用户回复一句短追问。
改写:"这项任务完成:搜索召回的几类漏检场景都堵上了,92 个自动化测试全绿,端到端跑通。
我直接提交收尾,不需要你做任何事。细节都在,想看哪部分说一声。"

**好例(保持)** — "已提交并推送到 origin/dev。远端有别人改了同文件邻近区域,rebase 干净无冲突,
改动完整保留。"——一句话讲清发生了什么、结果如何,做完的事不征询。
