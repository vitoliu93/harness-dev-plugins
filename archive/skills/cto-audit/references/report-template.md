# 审计报告骨架（八段）

证据规则贯穿全文：**每个论断配数字或 file:line**；issue 根因 ↔ 代码证据 ↔ 历史模式三方互证；子代理结论未经主上下文抽验不进报告。

## 1. 总体判断（一句话开头，不铺垫）

质量经济学句式：「交付速度 X，但质量经济学倒挂：缺陷占工作项 N%、fix 提交 M%——约几成产能在返工。根因是结构性的：<一句话根因>。」

## 2. 关键数字仪表盘

一张表：缺陷率 / fix 比例 / 代码量分布（受管控 vs 游离）/ 配置契约面 / CI 测试环节数 / issue 关联率等。每行带「含义」列。

## 3. 结构性缺陷（3~5 个，按严重度排序）

每个缺陷固定三段：**问题**（现象+量化）→ **证据**（file:line / 命令输出 / issue ident）→ **动作**（具体到可排期）。
带 P0/P1/P2 标注。安全类合并成至多一条、点到为止（见 SKILL.md 权重铁律）。

## 4. 模块缺陷聚类

来自 issue 路取证：哪个模块缺陷密度最高、什么类型反复出现、复发说明缺什么机制（回归测试/校验层/评测集）。

## 5. 流程与习惯

小表格：issue 关联率、巨型提交、self-merge、身份碎片、tag 体系、测试目录卫生。每行给低成本修法。

## 6. 值得肯定（必有，绿色调）

点名好实践 + 建议「保持并推广」。审计不公允则失去公信力，这一节不可省。

## 7. 战略层思考（1~2 条）

超出修 bug 的方向性判断：如编排机制二选一、超大 vendor 模块拆包、LLM 职责边界。有理由、有代价评估。

## 算法层二阶段报告（追加时）

- 按域分组（召回/对齐/LLM/管线/数据），每域 2~4 条
- 每条锚定真实事故 ident 或量化成本，不给教科书泛论
- 收尾一个「核心观察」：通常是「不缺想法、缺闭环」类的结构性总结 + 优先级表

## 交付变体

- HTML：仪表盘开屏大数字 + 缺陷编号卡（P 色带）+ 模块条形图 + roadmap 泳道 + 绿色「值得肯定」收尾；全中文为主避免术语堆砌；自包含无外链；深浅色 + 移动端可读
- 飞书：云盘上传 + 组织内链接可读 + 群发链接（不走文件消息）
- advanced-plan：goal（Done means 对齐路线图）/ spec（approach + key decisions + risks）/ todo（P0~P2 可认领 phase，各带 Acceptance）/ exploration（全部取证事实编号存档）
